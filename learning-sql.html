01

Joins beyond INNER

Joins combine rows from two or more tables on a related column. The type decides which rows survive when there's no match.

  • INNER JOIN — only rows with a match in both tables.
  • LEFT JOIN — every row from the left table; unmatched right columns come back NULL.
  • RIGHT JOIN — every row from the right table; the mirror of LEFT.
  • FULL OUTER JOIN — every row from both, matched where possible.
  • SELF JOIN — a table joined to itself (employee → manager in one table).
  • CROSS JOIN — every combination of rows. Rarely what you want by accident.
-- Customers and their orders, keeping customers with zero orders
SELECT c.customer_name, o.order_id, o.amount
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;
Interview favourite

To find customers with no orders: LEFT JOIN then filter WHERE o.order_id IS NULL. The unmatched rows are exactly the ones you want.

Q1You have employees(emp_id, name, manager_id). List each employee alongside their manager's name.

Self join — join the table to itself, aliased twice:

SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;

LEFT JOIN (not INNER) so the top boss, whose manager_id is NULL, still shows.

02

Aggregation & GROUP BY

Aggregate functions collapse many rows into one summary value. GROUP BY tells SQL what to collapse them by.

  • COUNT() counts rows; COUNT(col) skips NULLs, COUNT(*) doesn't.
  • SUM(), AVG() ignore NULLs entirely — worth remembering when averages look off.
  • COUNT(DISTINCT col) counts unique values only.
  • Every non-aggregated column in SELECT must appear in GROUP BY.
-- Revenue and order count per region, busiest first
SELECT region, COUNT(*) AS orders, SUM(amount) AS revenue
FROM orders
GROUP BY region
ORDER BY revenue DESC;
Q2From an orders table, find how many distinct customers placed an order in each month of 2025.
SELECT MONTH(order_date) AS mth,
       COUNT(DISTINCT customer_id) AS unique_customers
FROM orders
WHERE YEAR(order_date) = 2025
GROUP BY MONTH(order_date)
ORDER BY mth;

The DISTINCT inside COUNT is the key — without it you count repeat orders, not people.

03

WHERE vs HAVING

Both filter, but at different stages. One of the most common intermediate mix-ups.

  • WHERE filters individual rows before grouping. Can't use aggregates.
  • HAVING filters groups after aggregation. This is where aggregates live.
-- Regions with more than 100 orders AND only recent data
SELECT region, COUNT(*) AS orders
FROM orders
WHERE order_date >= '2025-01-01'   -- row filter first
GROUP BY region
HAVING COUNT(*) > 100;          -- group filter after
Rule of thumb

If your condition uses an aggregate like SUM() or COUNT(), it belongs in HAVING. If it's about a raw column value, use WHERE — it's faster because it cuts rows earlier.

Q3Find products whose total quantity sold across all orders exceeds 500 units.
SELECT product_id, SUM(quantity) AS total_qty
FROM order_items
GROUP BY product_id
HAVING SUM(quantity) > 500;

The threshold is on a sum, so it must be HAVING. Putting it in WHERE would error.

04

Subqueries & CTEs

A subquery is a query nested inside another. A CTE (Common Table Expression) is the same idea, named and placed up front with WITH — far more readable when logic stacks up.

  • Scalar subquery — returns one value, usable anywhere a value fits.
  • Correlated subquery — references the outer query; runs once per outer row (can be slow).
  • CTE — a named temporary result you reference like a table. Chain several with commas.
-- Customers who spent above the overall average, via CTE
WITH customer_totals AS (
    SELECT customer_id, SUM(amount) AS total_spent
    FROM orders
    GROUP BY customer_id
)
SELECT *
FROM customer_totals
WHERE total_spent > (SELECT AVG(total_spent) FROM customer_totals);
Why CTEs win

They read top-to-bottom like steps, can be referenced more than once, and make debugging easy — run each CTE on its own. Prefer them over deeply nested subqueries.

Q4Using a CTE, return the single most recent order per customer (customer_id, order_id, order_date).

Rank each customer's orders by date, then keep rank 1 — a CTE plus a window function:

WITH ranked AS (
    SELECT customer_id, order_id, order_date,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY order_date DESC
           ) AS rn
    FROM orders
)
SELECT customer_id, order_id, order_date
FROM ranked
WHERE rn = 1;
05

Window functions

The dividing line between intermediate and advanced. A window function computes across a set of rows without collapsing them — every row stays, but gains a value calculated over its window.

  • OVER() defines the window. Empty = the whole result set.
  • PARTITION BY splits rows into groups the function resets on (like GROUP BY, but rows survive).
  • ORDER BY inside OVER sets the order for running / positional calcs.
-- Each order's amount vs its region's average, rows intact
SELECT order_id, region, amount,
       AVG(amount) OVER (PARTITION BY region) AS region_avg
FROM orders;

Compare that to a GROUP BY: here you keep every order and see the regional average beside it — no join back required.

Q5For each row, show what percentage that order's amount is of its region's total revenue.
SELECT order_id, region, amount,
       ROUND(
         amount * 100.0 /
         SUM(amount) OVER (PARTITION BY region), 2
       ) AS pct_of_region
FROM orders;

The windowed SUM gives each row its region total without a separate GROUP BY and join.

06

Ranking & running totals

The most-used window functions in analyst work.

  • ROW_NUMBER() — unique sequential number, no ties.
  • RANK() — ties share a rank, then it skips (1, 2, 2, 4).
  • DENSE_RANK() — ties share a rank, no gap (1, 2, 2, 3).
  • LAG() / LEAD() — value from the previous / next row (great for period-over-period).
  • NTILE(n) — split rows into n roughly equal buckets (quartiles, deciles).
  • Running total: an aggregate with ORDER BY inside OVER.
-- Month-over-month revenue change with LAG
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS mom_change
FROM monthly_revenue;
-- Running / cumulative total of revenue by date
SELECT order_date, amount,
       SUM(amount) OVER (ORDER BY order_date
                        ROWS UNBOUNDED PRECEDING) AS running_total
FROM orders;
Q6Rank products by revenue within each category, top seller = rank 1. Which function if you don't want gaps after ties?

Use DENSE_RANK() (no gaps) and PARTITION BY category:

SELECT category, product_id, revenue,
       DENSE_RANK() OVER (
           PARTITION BY category
           ORDER BY revenue DESC
       ) AS rnk
FROM product_revenue;

Use ROW_NUMBER instead if you need exactly one winner even when revenues tie.

07

CASE & conditional logic

CASE is SQL's if/else. It shines for bucketing values and for conditional aggregation — turning rows into columns (pivoting).

-- Bucket customers by spend
SELECT customer_id, total_spent,
       CASE
         WHEN total_spent >= 10000 THEN 'VIP'
         WHEN total_spent >= 1000  THEN 'Regular'
         ELSE 'New'
       END AS tier
FROM customer_totals;
Power move

Wrap CASE inside SUM to pivot: SUM(CASE WHEN status='paid' THEN amount ELSE 0 END) gives a paid-revenue column beside other status columns — one row per group.

Q7In one row per region, show total revenue split into online_revenue and store_revenue from a channel column.

Conditional aggregation — CASE inside SUM:

SELECT region,
       SUM(CASE WHEN channel = 'online' THEN amount ELSE 0 END) AS online_revenue,
       SUM(CASE WHEN channel = 'store'  THEN amount ELSE 0 END) AS store_revenue
FROM orders
GROUP BY region;
08

Order of execution

You write SQL in one order, but the engine runs it in another. Knowing this explains a lot of "why won't my alias work?" errors.

Written order

SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT

Actual execution order

  • 1. FROM / JOIN — assemble the source rows
  • 2. WHERE — filter rows
  • 3. GROUP BY — group them
  • 4. HAVING — filter groups
  • 5. SELECT — pick columns, compute aliases
  • 6. ORDER BY — sort
  • 7. LIMIT — trim
The "aha"

Because SELECT runs after WHERE, an alias you create in SELECT can't be used in WHERE — the engine hasn't reached it yet. But it can be used in ORDER BY, which runs later. That single fact explains most alias errors.

Q8Why does SELECT amount*2 AS dbl FROM orders WHERE dbl > 100 error, and how do you fix it without repeating the expression?

WHERE runs before SELECT, so the alias dbl doesn't exist yet. Wrap it in a CTE so the alias is materialised before you filter:

WITH calc AS (
    SELECT order_id, amount * 2 AS dbl
    FROM orders
)
SELECT * FROM calc WHERE dbl > 100;

09

Stored procedures & scripting

A stored procedure is a named, reusable block of SQL saved in the database. Instead of pasting the same logic weekly, you call it once. In BigQuery these live inside a dataset with scripting extensions.

  • Why — reuse, consistency, one place to fix logic, and they take parameters.
  • Variables — DECLARE and SET hold values between statements.
  • Control flow — IF, WHILE, LOOP.
  • Call it — CALL dataset.proc_name(args).
-- Refresh a daily summary table for a given date
CREATE OR REPLACE PROCEDURE `proj.gold.refresh_daily_sales`(run_date DATE)
BEGIN
  -- remove existing rows for that date (idempotent re-runs)
  DELETE FROM `proj.gold.daily_sales` WHERE sales_date = run_date;

  -- insert freshly aggregated rows
  INSERT INTO `proj.gold.daily_sales` (sales_date, region, revenue, orders)
  SELECT run_date, region, SUM(amount), COUNT(*)
  FROM `proj.silver.orders`
  WHERE DATE(order_ts) = run_date
  GROUP BY region;
END;

CALL `proj.gold.refresh_daily_sales`('2026-08-19');
The idempotency trick

Notice the DELETE-then-INSERT for one date. That makes the procedure safe to re-run — running it twice for the same day won't double the numbers. This "delete the slice, reinsert the slice" pattern is the backbone of reliable daily pipelines.

Q9Why is a plain INSERT INTO ... SELECT inside a daily procedure dangerous if it runs twice, and what two approaches fix it?

A bare INSERT appends, so a second run duplicates that day's rows and inflates every downstream metric. Two fixes:

  • Delete-then-insert for the target slice (shown above).
  • MERGE (upsert) keyed on the unique columns — updates existing rows instead of adding new ones (next section).
10

INSERT / UPDATE / DELETE / MERGE

The DML statements that change data. As an analyst you read; as an engineer you write. MERGE is the one that separates beginners from the rest.

INSERT — add rows

INSERT INTO `proj.silver.orders`
SELECT * FROM `proj.bronze.orders_raw`
WHERE order_id IS NOT NULL;

UPDATE — change existing rows

UPDATE `proj.silver.customers`
SET city = 'Kuala Lumpur', updated_at = CURRENT_TIMESTAMP()
WHERE customer_id = 101;

DELETE — remove rows

DELETE FROM `proj.bronze.orders_raw`
WHERE _ingested_at < DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY);

MERGE — upsert (update if exists, insert if not)

MERGE `proj.silver.customers` AS t
USING `proj.bronze.customers_raw` AS s
ON t.customer_id = s.customer_id
WHEN MATCHED THEN
  UPDATE SET t.name = s.name, t.city = s.city, t.updated_at = CURRENT_TIMESTAMP()
WHEN NOT MATCHED THEN
  INSERT (customer_id, name, city, updated_at)
  VALUES (s.customer_id, s.name, s.city, CURRENT_TIMESTAMP());
Why MERGE matters

Without it you'd need separate UPDATE and INSERT passes plus logic to detect which rows are new. MERGE does both atomically on a key. This is exactly how you keep a silver table in sync with incoming bronze data every night.

Q10Daily data lands in bronze.customers_raw. Some customers are new, some changed city. Update the changed and add the new in one pass.

A textbook MERGE keyed on customer_id, exactly the pattern above. MATCHED → UPDATE the mutable columns; NOT MATCHED → INSERT the new record. One atomic upsert, no separate detection step.

11

Medallion architecture setup

The medallion pattern organises a warehouse into three quality layers. In BigQuery each layer is a dataset (BigQuery's word for a schema), and tables live inside them.

  • Bronze — raw, as-ingested data. Minimal changes. Your source of truth if anything downstream breaks.
  • Silver — cleaned, typed, deduplicated, conformed. The trustworthy working layer.
  • Gold — business-ready aggregates and models (star schema, KPIs) that feed Power BI.

Create the datasets (schemas)

CREATE SCHEMA IF NOT EXISTS `proj.bronze` OPTIONS(location='asia-southeast1');
CREATE SCHEMA IF NOT EXISTS `proj.silver` OPTIONS(location='asia-southeast1');
CREATE SCHEMA IF NOT EXISTS `proj.gold`   OPTIONS(location='asia-southeast1');

Define tables with types & partitioning

-- bronze: forgiving, keep an ingestion timestamp
CREATE TABLE IF NOT EXISTS `proj.bronze.orders_raw` (
  order_id     STRING,
  customer_id  STRING,
  amount       STRING,        -- raw text; cast later in silver
  order_ts     STRING,
  _ingested_at TIMESTAMP
);

-- silver: typed & partitioned by date for cheap, fast scans
CREATE TABLE IF NOT EXISTS `proj.silver.orders` (
  order_id     STRING,
  customer_id  STRING,
  amount       NUMERIC,
  order_ts     TIMESTAMP,
  updated_at   TIMESTAMP
)
PARTITION BY DATE(order_ts)
CLUSTER BY customer_id;
Partition & cluster

Partitioning by date means a query for one day scans one day's data, not the whole table — directly cutting cost and time in BigQuery. Clustering by a frequently-filtered column speeds lookups further. On big tables this is the difference between cents and dollars per query.

Bronze → Silver transform (clean & type)

CREATE OR REPLACE TABLE `proj.silver.orders` AS
WITH deduped AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY order_id ORDER BY _ingested_at DESC
         ) AS rn
  FROM `proj.bronze.orders_raw`
  WHERE order_id IS NOT NULL
)
SELECT order_id, customer_id,
       SAFE_CAST(amount AS NUMERIC)     AS amount,
       SAFE_CAST(order_ts AS TIMESTAMP)  AS order_ts,
       CURRENT_TIMESTAMP()               AS updated_at
FROM deduped
WHERE rn = 1;   -- keep only the latest version of each order
Q11Why keep amount as STRING in bronze but NUMERIC in silver, and what does SAFE_CAST protect you from?

Bronze should ingest everything without failing — a row with "N/A" in the amount would make a typed column reject the whole load. Keeping it STRING lets raw data land intact; silver then enforces types deliberately. SAFE_CAST returns NULL instead of erroring when a value can't convert, so one bad row won't kill the transform — you can filter or inspect the NULLs afterwards.

12

Automating data-in (ingestion)

Getting data into bronze. The source is usually files (CSV/JSON) in Google Cloud Storage. Two main routes: load jobs and external tables.

Option A — Load files from GCS into bronze (Python)

from google.cloud import bigquery

client = bigquery.Client(project="proj")

job_config = bigquery.LoadJobConfig(
    source_format=bigquery.SourceFormat.CSV,
    skip_leading_rows=1,
    write_disposition="WRITE_APPEND",   # add to bronze, don't overwrite
    schema=[
        bigquery.SchemaField("order_id", "STRING"),
        bigquery.SchemaField("customer_id", "STRING"),
        bigquery.SchemaField("amount", "STRING"),
        bigquery.SchemaField("order_ts", "STRING"),
    ],
)

uri = "gs://my-bucket/incoming/orders_*.csv"
load_job = client.load_table_from_uri(uri, "proj.bronze.orders_raw", job_config=job_config)
load_job.result()
print(f"Loaded {load_job.output_rows} rows into bronze")
write_disposition

WRITE_APPEND adds rows, WRITE_TRUNCATE replaces the whole table, WRITE_EMPTY only writes if empty. For bronze ingestion you usually append, then dedupe downstream in silver.

Option B — External table (query files in place)

CREATE OR REPLACE EXTERNAL TABLE `proj.bronze.orders_ext`
OPTIONS (
  format = 'CSV',
  uris = ['gs://my-bucket/incoming/orders_*.csv'],
  skip_leading_rows = 1
);
Q12Ingestion appends CSVs hourly. By silver you get duplicates when a file is re-delivered. Handle it at ingestion or later?

Handle it later, in the bronze→silver step. Let bronze stay append-only and complete (it's your raw record). Then dedupe in silver with ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY _ingested_at DESC) keeping rn = 1. This keeps ingestion simple and pushes cleaning to where it belongs.

13

Automating transforms (bronze → gold)

Once data lands, the layers refresh on a schedule. Two native ways in BigQuery, plus the procedure approach from section 09.

Scheduled queries

BigQuery can run a saved statement on a cron-like schedule. Best practice: have the schedule simply CALL a stored procedure so logic stays in one place.

-- What a daily 2am scheduled query would run
CALL `proj.gold.refresh_daily_sales`(CURRENT_DATE());

Chaining the layers in one procedure

CREATE OR REPLACE PROCEDURE `proj.gold.run_pipeline`()
BEGIN
  -- 1. bronze -> silver: clean, type, dedupe
  CREATE OR REPLACE TABLE `proj.silver.orders` AS
  SELECT order_id, customer_id,
         SAFE_CAST(amount AS NUMERIC) AS amount,
         SAFE_CAST(order_ts AS TIMESTAMP) AS order_ts
  FROM (
    SELECT *, ROW_NUMBER() OVER
           (PARTITION BY order_id ORDER BY _ingested_at DESC) rn
    FROM `proj.bronze.orders_raw`
    WHERE order_id IS NOT NULL
  ) WHERE rn = 1;

  -- 2. silver -> gold: business aggregate
  CREATE OR REPLACE TABLE `proj.gold.daily_sales` AS
  SELECT DATE(order_ts) AS sales_date, customer_id,
         SUM(amount) AS revenue, COUNT(*) AS orders
  FROM `proj.silver.orders`
  GROUP BY sales_date, customer_id;
END;
One call, whole pipeline

Now a single CALL proj.gold.run_pipeline() refreshes silver and gold in order. Schedule that one call and your medallion flow runs itself. Logic lives in the procedure; the scheduler just triggers it.

Q13Why schedule a CALL procedure() rather than pasting the full transform SQL into the scheduled query?

Separation of logic from scheduling. The procedure is version-controlled in one place; if the transform changes you edit the procedure, not the scheduler. Multiple schedules or manual runs all call the same tested logic, so no stale SQL drifts inside a forgotten scheduled query. It also makes the transform runnable on demand for backfills.

14

End-to-end orchestration in Python

Tying it together: one Python script that ingests, transforms, and validates — the kind of thing you'd schedule with Cloud Scheduler, cron, or Airflow.

from google.cloud import bigquery
import logging

logging.basicConfig(level=logging.INFO)
client = bigquery.Client(project="proj")

def run_query(sql):
    job = client.query(sql); job.result(); return job

def ingest_orders():
    cfg = bigquery.LoadJobConfig(
        source_format=bigquery.SourceFormat.CSV,
        skip_leading_rows=1, write_disposition="WRITE_APPEND",
    )
    job = client.load_table_from_uri(
        "gs://my-bucket/incoming/orders_*.csv",
        "proj.bronze.orders_raw", job_config=cfg,
    )
    job.result()
    logging.info(f"Ingested {job.output_rows} rows")

def transform():
    run_query("CALL `proj.gold.run_pipeline`()")
    logging.info("Silver + gold refreshed")

def validate():
    sql = "SELECT COUNTIF(revenue IS NULL) AS bad FROM `proj.gold.daily_sales`"
    bad = list(run_query(sql).result())[0].bad
    if bad > 0:
        raise ValueError(f"Validation failed: {bad} null revenue rows")
    logging.info("Validation passed")

if __name__ == "__main__":
    ingest_orders(); transform(); validate()
    logging.info("Pipeline complete")
The shape to remember

Ingest → transform → validate, with the transform delegated to a stored procedure and a validation step that raises on bad data so the scheduler marks the run as failed. A pipeline that silently produces wrong numbers is worse than one that loudly stops.

Q14Why end with a validation step that raises, instead of trusting the transforms? Give a concrete example of what it catches.

Transforms can succeed technically while producing bad data. Example: an upstream source changes its timestamp format, so SAFE_CAST(order_ts AS TIMESTAMP) silently returns NULL for every new row — no error, but gold now has null dates and revenue goes missing from dashboards. A validation query that counts NULLs and raises turns that silent corruption into a visible failed run, so you catch it before management sees a broken dashboard. Fail loud, fail early.
